## 응용 설계에서 정한 것

- shm 링: 채널당 16칸. E1에서 4칸은 작은 메시지 처리량이 pipe의 약 1/13이었고, 16칸에서 64B가 pipe와 비슷해졌다.

## 워크로드 (기본 조건)

| 항목 | 값 |
|---|---|
| 오디오 | 16비트 부호 있는 PCM, 모노, 48kHz |
| 청크 크기 | 4KB, 16KB, 64KB, 256KB. 실행마다 한 크기로 고정 |
| 응답 | 통계 모드: 수십 바이트 / 정규화 모드: 요청과 같은 크기 |
| 요청 빈도 | closed-loop, 창 크기 1 |
| 동시 클라이언트 | 1, 2, 4, 8 |
| 공유 자료구조 | 청크마다 클라이언트별 통계 쓰기 1회, 전체 통계 읽기 1회, 전체 통계 쓰기 1/K회(K=8), 작업 큐 넣기 1회와 꺼내기 1회 |

기본 조건은 청크 4 x 클라이언트 4 x 모드 2 x IPC 2 = 64개다.
추가 조건(측정 시간이 허락하면): 창 크기 4, K = 1과 64, 섞인 크기 분포. 첫 측정에서 조건당 시간을 보고 정한다.

## 예측

| 번호 | 조건 | 예측 | 1단계 근거 |
|---|---|---|---|
| P1 | 청크 4KB~16KB, 통계 모드 | 두 방식이 비슷하고, 4KB는 pipe가 약간 앞선다 | 16칸 링에서 1KB 처리량이 shm 865,609, pipe 987,189 msg/s로 pipe가 1.14배였다(E1). 16KB는 4칸 링에서도 pipe 129,528, shm 120,303 msg/s로 거의 같았다 |
| P2 | 청크 64KB~256KB, 통계 모드 | shm이 빠르지만 차이는 1단계 배수(256KB 왕복 5.6배)보다 작다 | 256KB 왕복 지연 pipe 439us, shm 78us. pipe는 64KB마다 끊겨 256KB에 문맥 교환 4.04회. 응용에서는 청크 분석 시간이 양쪽에 똑같이 더해진다. 얼마나 줄지는 모른다 |
| P3 | 청크 256KB, 정규화 모드 | shm의 이득이 통계 모드보다 크다 | 응답도 256KB라 pipe는 64KB마다 끊기는 비용을 양방향으로 낸다 |
| P4 | 클라이언트 8개 | shm의 처리량 이점은 유지되지만, p99 지연 차이는 중앙값 차이보다 작다 | 1단계 클라이언트 8개, 1MB에서 pipe 중앙값이 더 짧았다. 응용 청크는 256KB 이하라 E5의 1MB 결과는 근거로 쓰지 않는다 |
| P5 | 메모리 (클라이언트 8개) | shm 서버가 링 크기만큼 더 쓴다 | 16칸 x 256KB x 클라이언트 8 = 약 32MB |

1단계 초안에서 뺀 예측: "작은 응답이 shm 이득을 깎는다". E1에서 작은 메시지 열세의 원인이 링 4칸으로 확인되어 뺐다.
