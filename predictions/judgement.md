- 4KB는 클라이언트 1, 2에서 같고 4, 8에서 pipe가 약간 앞선다. 16KB는 shm이 3~13% 앞선다. 차이가 모두 15% 안이라 "비슷하다"는 예측과 맞는다.
- 원인 근거(strace, 청크당 IPC 시스템 콜 수): 4KB에서 shm은 세마포어 호출이 클라이언트 4.00 + 서버 5.0~5.1 = 약 9회다. pipe는 c1에서 8.0회, c8에서 7.0회다. 복사가 작은 크기에서는 shm의 복사 절약보다 호출 수 차이가 앞선다.

  3번 중 2번이 반대다. 정규화 모드 배수(1.38~1.67)는 비교적 안정적이고, 통계 모드 배수(1.39~2.49)가 크게 흔들린다.
- 원인 추정: 클라이언트 8개에서는 서버 워커 4개가 계산으로 꽉 찬다. E0 서버 구간 기록에서 정규화 모드 256KB의 처리 시간 중앙값은 1010us(shm), 1090us(pipe)로 통계 모드(406, 502us)의 2배가 넘는다. 큐 대기도 클라이언트 4개의 46us(shm)에서 8개의 279us로 늘었다. 양쪽에 똑같이 더해지는 계산과 대기가 커져서 IPC 차이가 묽어진 것이다. 예측은 "pipe가 양방향으로 끊기는 비용"만 보고, 정규화 계산이 워커를 포화시키는 효과를 빠뜨렸다.
- strace로는 설명되지 않는다: shm의 청크당 세마포어 호출 수는 통계, 정규화 모두 약 9회다.

- "처리량 이점 유지"는 64KB 이상에서는 맞고, 4KB 통계 모드에서는 틀렸다. E0에서는 pipe가 1.16배 앞섰다(shm 0.86). 같은 조건을 다른 세션 9번(E0, E1 2번, E2 6번)에서 비교하면 shm/pipe 처리량이 0.79~1.23, 중앙값 1.04다. 4KB에서 shm의 이점은 없고 두 방식이 같다고 보는 것이 맞다.
- 원인 근거(strace, stats 4K): 클라이언트 1개에서 8개로 늘 때 pipe 서버의 poll은 청크당 2.00회에서 1.03회로 줄었다(poll 한 번으로 준비된 여러 클라이언트를 받음). shm 서버의 세마포어 호출은 5.01회에서 5.02회로 그대로다. 그래서 8개에서는 shm이 청크당 IPC 호출을 약 2회 더 부른다(9.1 대 7.0). 호출 한 번의 비용(System V 세마포어 처리)이 원인인지는 재지 않았다.

## P5 메모리, 클라이언트 8개: 256KB에서만 맞음

| 모드 | 크기 | 서버 VmHWM MB pipe / shm | 차이 |
|---|---|---|---|
| stats | 4K | 19.4 / 20.5 | +1.1 |
| stats | 16K | 19.5 / 22.1 | +2.6 |
| stats | 64K | 20.0 / 28.2 | +8.2 |
| stats | 256K | 21.6 / 53.2 | +31.6 |
| norm | 4K | 19.4 / 20.6 | +1.2 |
| norm | 16K | 19.5 / 22.5 | +3.0 |
| norm | 64K | 19.7 / 30.1 | +10.3 |
| norm | 256K | 21.4 / 60.9 | +39.5 |

- 256KB 통계 모드의 +31.6MB는 예측한 32MB(요청 링 16칸 x 256KB x 8)와 맞는다. 정규화 모드는 응답 링(채널당 4칸 x 256KB x 8 = 8MB)까지 써서 +39.5MB이고, 실제 세그먼트 크기 약 40MB(41,957,376바이트)와 맞는다. 응답 링은 예측 뒤 11/27 설계에서 더해졌다(`predictions.md` 변경 기록).
- 작은 청크에서 차이가 작은 이유: VmHWM은 실제로 건드린 페이지만 센다. 칸 하나는 256KB 크기로 잡혀 있어도 4KB 청크는 앞의 1~2페이지만 쓴다. 16칸 x 8채널 x 약 8KB = 약 1MB로 +1.1MB와 맞는다. "링 크기만큼"이 아니라 "실제로 쓴 칸 크기만큼" 더 쓴다고 고쳐 말해야 한다.
- 클라이언트도 shm 쪽이 더 쓴다(256KB 정규화: pipe 5.5MB, shm 10.5MB). 자기 슬롯을 매핑하고 건드리기 때문이다.
- E5(제자리 처리)로 256KB 정규화 c8 서버 VmHWM을 61.2MB에서 51.4MB로 줄였다(`data/app/e5_*`).

## 측정 간 변동 (판정의 한계)

- 같은 코드, 같은 조건을 다른 세션에서 다시 재면 지연이 20~50% 달라졌다. 예: shm 정규화 256K c2 지연이 E0에서 783us, E5 기본판 실행에서 1227us였다.
- E1/E2에서 락 대기는 모든 설정에서 청크당 0.36~1.12us로 지연(180~3000us)의 0.5% 안팎이었다. 그런데도 같은 설정의 지연이 20~30% 흔들렸으므로, 흔들림은 락이 아니라 측정 환경(WSL2, CPU 클럭과 스케줄링)에서 온 것으로 본다.
- 그래서 배수 차이가 이 변동보다 작은 판정(P1 전체, P3 클라이언트 2, P4의 4KB)은 "같다"로 읽는다. 세션을 바꿔도 방향이 유지된 것(P2 전체, P3 클라이언트 8의 반대 3번 중 2번, P5)만 확정 판정으로 쓴다.
