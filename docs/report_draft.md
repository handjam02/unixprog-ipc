## 1. 문제 정의 및 요구사항 분석

### 1.1 문제 정의 및 설계과제 목표

- 응용: 녹음된 오디오를 청크 단위로 서버에 보내 일괄 분석하는 서버
  - 입력: 16비트 PCM, 모노, 48kHz 청크 (4KB ≈ 43ms 분량, 256KB ≈ 2.7초 분량)
  - 통계 모드: 서버가 RMS, 피크, 무음 구간 수, "이 청크 RMS / 전체 평균 RMS"를 계산해 32바이트로 응답
  - 정규화 모드: 피크가 0.9가 되도록 고친 오디오 전체를 응답 (요청과 같은 크기)
- 실시간 속도 가정은 버림
  - 실시간 오디오 1채널 = 48,000 × 2B = 96,000 B/s. 이 속도면 어떤 IPC를 써도 차이가 안 남
  - 그래서 "녹음 파일을 최대한 빨리 일괄 분석" 시나리오로 잡음 (기획서 5.1절)
- IPC 선택이 중요한 이유
  - 청크 크기가 4KB~256KB로 넓음. 측정 노트북의 pipe 버퍼가 64KB라 64KB를 넘으면 pipe는 한 번에 못 보냄
  - 응답 크기를 모드로 바꿀 수 있음 (32B vs 요청과 같은 크기) → 요청·응답 비대칭이 IPC 비용에 주는 영향을 볼 수 있음
  - 서버에 여러 워커가 함께 쓰는 공유 통계(클라이언트별 통계, 전체 통계, 작업 큐)가 있어 IPC 외 동기화 비용도 함께 드러남
- 목표: 1단계 측정으로 예측을 세우고, 2단계 응용(pipe 버전, shm 버전)에서 예측이 맞는지 직접 잰 수치로 확인하고, 1회 이상 설계 개선

### 1.2 요구사항 분석

**기능 요구사항**

1. 클라이언트
   - 시드로 정한 PCM(사인파·잡음·무음 섞음)을 메모리에서 만들어 청크로 보냄 (디스크 I/O가 측정에 섞이지 않게)
   - 응답을 받아 요청 지연을 기록하고, seq와 크기로 응답을 검증
   - 결과를 CSV로 저장 (측정 구간 밖)
2. 서버
   - 여러 클라이언트의 청크를 받아 분석, 클라이언트별 통계·전체 통계 갱신, 응답 전송
   - 통계 보고 스레드가 주기적으로 전체 통계를 읽어 기록
   - Ctrl+C(SIGINT)/SIGTERM에 같은 순서로 정리하고 IPC 자원 해제
3. 메시지: HELLO, CHUNK, RSP_STATS, RSP_AUDIO, BYE (`app/ipc.h`)

**비기능 요구사항**

- 동시 클라이언트: 최대 8개 (`APP_MAX_CLIENTS 8`, 논리 CPU 8개와 같게)
- 처리량 하한: 실시간 8채널분 8 × 96,000 B/s = 768,000 B/s (기획서 5.3절)
  - 실측: 64KB 통계 모드 클라이언트 8개 처리량 pipe 725.91 MB/s, shm 1,054.58 MB/s (E0) → 하한의 수백 배 이상
- 요청 지연 목표(클라이언트 8, 64KB/256KB, 통계 모드): [확인 필요]
- 메모리 목표(서버 VmHWM 상한): [확인 필요] — 설계상 shm 세그먼트 약 40MB (4.3절)

**제약 조건과 충족 방법**

### 2.2 벤치마크 설계

- 구조 (`phase1/`)
  - `fork`로 서버(자식)와 클라이언트(부모)를 나누고, 클라이언트 스레드마다 전용 채널
  - pipe 버전: 채널마다 익명 pipe 2개(요청용, 응답용), 블로킹 read/write
  - shm 버전: System V shm(key 60071)을 채널로 나눈 링 버퍼 + System V 세마포어(key 60072, 채널당 EMPTY/FULL/RESP 3개). 본 측정의 링은 4칸
  - 두 버전이 같은 드라이버(`bench.c`)를 쓰고 IPC 부분만 다름
- 왕복 지연 (ping-pong)
  - 클라이언트가 헤더 16B + payload를 보내고 서버가 같은 크기로 돌려줌
  - t0: 요청을 IPC로 내보내기 직전 (shm은 빈 칸 P 연산과 공유 메모리 복사가 t0 뒤라 측정에 포함)
  - t1: 응답을 클라이언트 버퍼로 끝까지 읽은 직후
  - 이유: 양방향 복사와 상대 프로세스를 깨우는 비용을 다 넣고, 송신 버퍼 채우는 시간은 빼려고
  - 스레드마다 워밍업 20회 버리고 100회 기록 → 클라이언트 N개면 표본 N × 100개
- 처리량
  - barrier로 모든 클라이언트 스레드를 맞춰 출발, 각자 k개를 응답 없이 연달아 보내고 마지막만 STREAM_ACK
  - t_start: barrier 통과 직후, t_end: ACK 응답 수신 직후. 반복 1회 시간 = 가장 이른 t_start ~ 가장 늦은 t_end
  - 워밍업 2회 뒤 30회 기록. 1회에 스레드당 약 16MB가 되도록 k 자동 결정(16~10,000개)
- 전체 워밍업: 첫 조건 전에 8개 채널로 1초 왕복 (기록 안 함)
- 시간: `clock_gettime(CLOCK_MONOTONIC)`, 측정 중에는 `uint64_t` 배열에만 저장. 검증(memcmp), printf, CSV는 측정 뒤
- 변인: 메시지 64B, 1KB, 16KB, 256KB, 1MB (5단계) × 클라이언트 1, 2, 4, 8
  - 참고: 기획서 4.2절은 4KB, 64KB를 넣은 7단계였는데 실제 본 측정은 5단계로 진행
- 자원: 조건 전후 `getrusage(RUSAGE_SELF)` 차이(user/sys 시간, 자발적/비자발적 문맥 교환), 조건 끝 시점 `/proc/self/status` VmRSS. 서버 값은 측정 구간 밖에서 받아 옴
- p99: nearest-rank (정렬 후 ceil(0.99n)번째)

### 2.4 결과 해석

1. 큰 메시지(256KB, 1MB)는 클라이언트 1개에서 shm이 확실히 유리
   - 256KB 중앙값 pipe 439.28µs vs shm 77.95µs (5.6배), 처리량 4,740 vs 64,117 msg/s (13.5배)
   - 근거: pipe 버퍼가 64KB라 256KB는 여러 번 나뉘어 오가고, 그때마다 쓰는 쪽이 잠들고 깨어남
     - 클라이언트 자발적 문맥 교환 왕복당 약 9.0회(pipe) vs 1.0회(shm)
     - 클라이언트 sys 시간 23.60ms vs 0.34ms → pipe는 복사가 커널 안(read/write)에서 일어나고, shm은 사용자 공간 memcpy라 sys 시간이 거의 없음
2. 작은 메시지 처리량은 pipe가 압도적, 원인은 shm 링 칸 수
   - 64B 처리량 pipe 1,533,299 vs shm(4칸) 117,242 msg/s (13배 차이)
   - 추가 실험 E1: 링만 16칸으로 늘리자 1,485,383 msg/s → pipe와 비슷해짐. 원인이 IPC 종류가 아니라 링 4칸이었음을 그 요인만 바꾼 실험으로 확인
   - 이 결과로 응용 shm 링을 채널당 16칸으로 정함
3. 순위가 바뀌는 지점
   - 클라이언트 1개 지연: 64B는 pipe, 1KB~16KB는 비슷, 256KB부터 shm
   - 클라이언트 8개 지연: 256KB(169.81 vs 221.96µs)와 1MB(903.09 vs 991.73µs)에서 pipe 중앙값이 오히려 짧음 → 클라이언트 1개와 순위가 뒤집힘
   - 클라이언트 8개 처리량: 64B는 pipe 4.4배, 16KB부터 shm이 앞섬
4. 예상과 다른 결과: 클라이언트가 많을수록 지연이 짧아지는 구간
   - pipe 256KB 중앙값: 클라이언트 1개 439.28µs → 8개 169.81µs. 64B도 3.62(1개) → 49.69(2개) → 6.09(8개)로 들쭉날쭉
   - 추정 원인: 클라이언트 1개일 때는 상대 스레드가 잠든 CPU(WSL2에서는 하이퍼바이저에 반납된 가상 CPU)에서 깨어나는 시간이 지연에 그대로 들어가고, 8개일 때는 다른 스레드 때문에 CPU가 깨어 있음 (`phase1/README.md`)
   - 추가 실험으로는 아직 확인 안 함. `taskset -c 0`으로 한 CPU에 고정한 측정과 비교 예정 [실측값 확인 필요]
   - 지연 분포 그래프(p1_latency_hist.png)의 두 묶음 여부 [확인 필요]
5. 값의 흔들림
   - E5에서 같은 명령 5회의 클라이언트 8개 256KB 처리량이 53,336~112,378 msg/s (2.1배 범위)
   - 회차가 갈수록 떨어지는 경향. 발열 추정이나 확인은 안 함 → 응용 측정에서 조건 사이 2초 쉬기(`run_app.sh -P 2`), 같은 조건의 pipe/shm을 연달아 측정

| 메시지 종류와 크기(분포) | 요청: 헤더 24B + PCM 청크 4KB / 16KB / 64KB / 256KB (실행마다 한 크기 고정). 응답: 통계 모드 헤더 + 32B, 정규화 모드 헤더 + 요청과 같은 크기 |
| 요청 빈도 (클라이언트당) | closed-loop, 창 크기 1 (응답을 받으면 바로 다음 청크). 실행마다 워밍업 100개 + 기록 1,000개 |
| 통신 패턴 | N:1 요청-응답 (클라이언트 N개 → 서버 1개) |
| 서버 공유 자료구조와 읽기/쓰기 비율 | 청크 1개당 클라이언트별 통계 쓰기 1회, 전체 통계 읽기 1회, 전체 통계 쓰기 1/K회(K=8), 작업 큐 넣기 1회·꺼내기 1회. 통계 보고 스레드가 100ms마다 둘 다 읽기 |
| 동시 클라이언트 수 | 1, 2, 4, 8 |

- 기본 조건(E0): 청크 4 × 클라이언트 4 × 모드 2 × IPC 2 = 64조건, 조건당 30회
- 추가 조건 후보(창 크기 4, 섞인 크기 분포)는 측정하지 않음

### 4.3 공유 자원 정의와 동기화 설계

1. 작업 큐 (`common/queue.c`)
   - 접근: 서버 수신 스레드(생산자), 워커 W개(소비자)
   - 기법: mutex 1개 + 조건 변수 2개(`not_full`, `not_empty`), 16칸 원형 큐
   - 이유: 생산자-소비자 패턴. 가득 차면 수신 스레드가 기다려 역압이 생김. 넣은 시각을 같이 넣어 큐 대기 시간을 잴 수 있음
2. 클라이언트별 통계 테이블 (`common/stats.c`)
   - 접근: 워커(청크마다 쓰기), 통계 보고 스레드(읽기)
   - 기법: 클라이언트별 mutex 8개 (`-L per`, 기본). 비교: 테이블 전체 mutex 1개 (`-L table`, E1)
   - 이유: 쓰기가 대부분이라 rwlock 이득 없음. 다른 클라이언트의 청크를 처리하는 워커끼리 안 막히게 락 범위를 클라이언트 단위로 나눔
3. 전체 통계 (`common/stats.c`)
   - 접근: 워커(청크마다 읽기 1회, K청크마다 쓰기 1회), 통계 보고 스레드(읽기)
   - 기법: `pthread_rwlock` (기본). 비교: mutex (`-G mutex`, E2)
   - 쓰기 줄이기: 워커마다 `stats_pending_t`에 K개(기본 8) 모았다가 한 번에 반영
   - 이유: 읽기가 쓰기보다 K배 많아 읽기끼리 동시 진행을 허용
4. shm 슬롯 표 (shm 버전, `ipc_shm.c`)
   - 접근: 클라이언트 프로세스들(접속), 서버 수신 스레드(새 접속 확인, 해제)
   - 기법: 세그먼트 안의 프로세스 공유 mutex, `PTHREAD_MUTEX_ROBUST`
   - 이유: 접속·종료 때만 바뀜. 잡은 채로 클라이언트가 죽어도 `EOWNERDEAD` → `pthread_mutex_consistent`로 이어 씀
5. shm 요청 링 (슬롯당 16칸)
   - 접근: 클라이언트 송신 스레드 1개 → 서버 수신 스레드 1개
   - 기법: System V 카운팅 세마포어 REQ_EMPTY(초기 16), REQ_FULL(0). 읽기/쓰기 위치는 각자 따로 셈
   - 클라이언트는 REQ_FULL과 NOTIFY를 `semop` 한 번으로 함께 올림 → 서버 수신 스레드는 NOTIFY 하나만 기다린 뒤 링을 훑음
6. shm 응답 링 (슬롯당 4칸)
   - 접근: 서버 워커 여러 개 → 클라이언트 수신 스레드 1개
   - 기법: RSP_EMPTY(초기 4), RSP_FULL(0) + 슬롯별 mutex `wmu`로 워커끼리 줄 세움
7. pipe 응답 FIFO (pipe 버전)
   - 접근: 워커 여러 개 → 클라이언트 수신 스레드
   - 기법: 클라이언트별 응답 mutex. 4KB(PIPE_BUF)보다 큰 write는 원자적이지 않아 창 크기 2 이상에서 응답이 섞일 수 있기 때문
8. System V 세마포어를 고른 이유
   - 1단계 벤치마크와 같은 방식이라 결과 비교가 쉬움
   - `ipcs` 한 번으로 shm과 세마포어 정리 여부를 같이 확인 가능
   - `SEM_UNDO`는 안 씀: 카운팅 세마포어의 P와 V를 서로 다른 프로세스가 하기 때문. 대신 슬롯을 비울 때 서버가 세마포어 값을 초기값으로 되돌림(`sem_reset_slot`)

**경쟁 상태·교착 상태 방지**

1. 락 순서 규칙: 두 개를 함께 잡을 때는 "클라이언트별 통계 → 전체 통계" 순서만. 실제 `stats.c`는 둘을 겹쳐 잡지 않음
2. 작업 큐 락을 잡은 채로 IPC 송수신이나 다른 락을 기다리지 않음
3. 통계 보고 스레드는 클라이언트별 락을 하나씩, 그다음 전체 락 (겹치지 않음)
4. 상대 프로세스가 kill -9로 죽어도 세마포어는 안 풀림 → 막힐 수 있는 대기는 전부 `semtimedop`(100ms) + `kill(pid, 0)` 생존 확인
5. 검증
   - 합계 검사: 조건마다 클라이언트 `sent_chunks` 합 = 서버 chunks = 전체 통계 청크 수. E0~E5 전체 136조건(E0 64, E1 16, E2 24, E5 32)에서 `match` 모두 1, 잘못된 응답(`bad_rsp`) 0 (`figures/tables/checks_all.csv`)
   - `make tsan`(ThreadSanitizer) 경고 없음 (ai_log 기록: pipe 256K norm 창 4 클라이언트 8개, shm 10,800청크) [캡처 삽입: make tsan 실행 결과]
6. 알려진 한계: 클라이언트가 BYE 없이 죽으면 큐에 남은 그 클라이언트의 응답이 같은 번호를 새로 받은 클라이언트에게 갈 수 있음. 번호를 돌아가며 주고(`next_hint`), 클라이언트가 seq·크기를 검사해 잘못된 응답을 셈

## 5. 시스템 구현 및 데모

### 5.1 소스코드 주요 부분 설명

**모듈 구조**

- `app/ipc.h`: 두 버전 공통 인터페이스
  - 서버: `server_open`, `server_recv`(수신 스레드 전용), `server_send`(워커들이 동시에), `server_chunk_free`, `server_stop`(시그널 스레드), `server_close`, `ipc_server_option`
  - 클라이언트: `client_connect`, `client_send`(송신 스레드), `client_recv`(수신 스레드), `client_close`
  - 정리: `ipc_cleanup` (`make cleanipc`, `server_open`이 부름)
  - 원칙: 타임스탬프·통계·분석·작업 큐는 IPC 층에 넣지 않음 → 두 버전의 차이가 IPC 부분에서만 나오게
- `Makefile`: 패턴 규칙 `app/server_%: app/server.c app/ipc_%.c ...`로 같은 `server.c`에 구현 하나를 붙여 `server_pipe` / `server_shm` 생성. `-DIPC_NAME`으로 결과 파일 이름 구분

**pipe 버전 (`app/ipc_pipe.c`)**

1. 생성·접속: 클라이언트가 req/rsp FIFO를 `mkfifo` → rsp를 `O_RDONLY|O_NONBLOCK`로 열기 → 공개 FIFO에 HELLO(32B, PIPE_BUF 이하라 섞이지 않음) → 서버 수신 스레드가 rsp를 쓰기로, req를 읽기로 열고 번호 응답 → 클라이언트가 req를 씀으로 열기. FIFO open이 서로를 기다리며 막히지 않는 순서
2. 수신: 수신 스레드 하나가 `poll()`로 모든 req FIFO를 보고, 준비된 fd마다 `read()`를 한 번만 불러 클라이언트별 수신 상태(헤더/본문 읽은 양)를 채움. 256KB가 64KB씩 나뉘어 와도 다른 클라이언트가 안 기다림
3. 송신: `writev`로 헤더+본문을 함께 보내고, 나뉘어 써지면 남은 만큼 반복 (`write_msg`). 응답은 클라이언트별 mutex 안에서 끝까지 씀
4. 해제: 클라이언트는 BYE 뒤 자기 FIFO `unlink`. BYE 없이 EOF가 오면 서버가 그 클라이언트 FIFO를 지움. 서버 종료 때 공개 FIFO `unlink`. `server_stop`은 자기 pipe에 1바이트를 써서 `poll`을 깨움

**shm 버전 (`app/ipc_shm.c`)**

1. 생성: `ipc_cleanup()`으로 남은 같은 key 자원 삭제 → `shmget(60070, IPC_CREAT|IPC_EXCL)` → `shmat` → `semget(60073, 33개)` → `semctl(SETALL)`로 초기값 → 슬롯 표 robust mutex 초기화 → 마지막에 magic 기록(release)
2. 접속: 클라이언트가 슬롯 표 mutex를 잡고 빈 슬롯을 USED로, gen 1 증가 → NOTIFY 올림. 서버 수신 스레드는 훑을 때 gen이 바뀐 것을 보고 받아들임
3. 송신(클라이언트): `REQ_EMPTY` P → 칸에 헤더+payload memcpy → `REQ_FULL`과 `NOTIFY`를 한 번의 `semop`으로 V
4. 수신(서버): NOTIFY P → rr 다음 슬롯부터 훑어 `REQ_FULL`을 `IPC_NOWAIT`으로 P → 기본판은 칸에서 `xmalloc` 버퍼로 복사 후 칸 반환(`REQ_EMPTY` V)
5. 응답(워커): 슬롯 `wmu` 잡고 `RSP_EMPTY` P(100ms마다 클라이언트 생존 확인) → 응답 칸에 memcpy → `RSP_FULL` V
6. 해제 순서 (`server_close`): magic 0(새 접속 막음) → `shmdt` → `shmctl(IPC_RMID)` → `semctl(IPC_RMID)`. 세마포어 집합을 지우면 붙어 있던 클라이언트 대기가 `EIDRM`으로 바로 끝남
7. kill -9 대비: 서버는 `WAIT_MS`(100ms)마다 USED 슬롯 pid를 `kill(pid,0)`로 확인해 죽은 슬롯을 비움. 클라이언트는 서버 pid가 죽었으면 -1

**공유 자원 동기화 코드**

- `server.c` `worker_main`: 분석 → `stats_global_mean`(전체 읽기) → `stats_client_add`(클라이언트별 쓰기) → `stats_global_add`(K개 모아 전체 쓰기) → `server_send`. 락 대기 시간은 lock 호출 직전~반환 직후를 `lockwait_t`에 더함
- 종료 순서: `server_stop` → `server_recv`가 -1 → 수신 스레드가 `wq_close` → 워커가 큐를 비우고 끝 → 보고 스레드 종료 → join → CSV 저장 → `server_close`

**설계 개선 E5 (`-X inplace`)**: 6.5절

## 6. 성능 측정과 분석

### 6.1 현실적 제한 요소의 반영

1. 경쟁 상태 방지: 4.3절의 자료구조별 락, 락 순서 규칙, 합계 검사(136조건 모두 일치, 잘못된 응답 0), `make tsan`
2. 성능 향상
   - shm 링 16칸 (1단계 E1 근거)
   - pipe 수신을 poll + 부분 읽기로 만들어 256KB 청크 하나가 다른 클라이언트를 막지 않게 함
   - 전체 통계 쓰기를 K개 묶음으로 (E2에서 확인)
   - 클라이언트별 통계 락 (E1에서 비교)
   - shm 제자리 처리 (E5, 6.5절)
3. 메모리 절감
   - shm 세그먼트가 칸마다 최대 청크(256KB) 크기라 메모리를 많이 씀 → E5에서 응답 칸 payload를 쓰지 않게 해 서버 VmHWM 감소 확인 (6.5절)
   - 클라이언트 PCM은 시작 때 5초 분량 표 하나만 만들고 잘라 씀
4. 스레드 수: 서버 7개(기본), 클라이언트 3개 + main
5. make: 버전별 빌드와 전체 빌드, tsan 빌드, cleanipc
6. 두 버전의 공정성: 같은 `server.c`/`client.c`, 수신 스레드 1개 + 워커 W개 구조를 두 버전에 같이 씀. shm 기본판도 칸 → 큐 버퍼로 복사해 pipe와 같은 구조를 맞춤

### 6.2 측정 방법

- 측정 스크립트: `scripts/run_app.sh` (E0 기본, `-E`로 서버 옵션을 바꾼 추가 실험)
  - 순서: 모드 → 크기 → 클라이언트 수 → IPC. 같은 조건의 pipe와 shm을 연달아 측정
  - 조건마다 서버를 새로 띄우고 30회 연달아 실행 → 서버 rusage·VmHWM이 조건별 값
  - 조건 사이 2초 쉬기, 측정 환경은 결과 폴더 `env.txt`에 기록
- 측정 지점 (`clock_gettime(CLOCK_MONOTONIC)`)
  1. 요청 지연: 클라이언트 송신 스레드의 송신 직전 ~ 수신 스레드가 응답을 다 받은 직후. 사용자가 체감하는 전체 시간. 응답 검증은 타임스탬프 뒤
  2. 큐 대기: 서버 수신 스레드가 큐에 넣은 때 ~ 워커가 꺼낸 때
  3. 처리: 워커의 분석(+정규화) 시작 ~ 끝
  4. 락 대기: lock 호출 직전 ~ 반환 직후 (클라이언트별, 전체 읽기, 전체 쓰기 3종)
  5. 응답 송신: `server_send` 호출 ~ 반환
- 반복: 실행마다 클라이언트 하나가 워밍업 100청크를 버리고 1,000청크를 기록. 조건당 30회 → 표본 30 × N × 1,000개
- 처리량: 클라이언트별 기록 1,000청크 / 소요 시간 (`chunks_per_s`, `mb_per_s`는 요청 payload 기준)
- 자원: 클라이언트·서버 모두 `getrusage(RUSAGE_SELF)` 전후 차이(user/sys, 자발적/비자발적 문맥 교환), 끝날 때 `/proc/self/status` VmRSS, VmHWM
- 간섭 최소화: 측정 구간 안에서 파일 쓰기·printf 안 함. 값은 메모리 배열에 모았다가 끝난 뒤 저장. PCM 생성은 표에서 복사만

**맞은 부분과 근거**

1. P2: 차이가 1단계보다 작아진 이유 = 같은 청크 분석 시간이 양쪽에 더해지고, IPC 차이 자체도 줄었음
   - 청크 분석 비용: 서버 user 시간이 청크당 pipe 325.3µs, shm 456.6µs (256KB stats, 클라이언트 1개). 1단계 256KB 왕복 중앙값(78~439µs)과 같은 규모
   - 서버 CPU 합계는 거의 같음 (pipe 561.6 vs shm 548.4µs/청크). 복사가 pipe는 커널(sys 236.3µs), shm은 사용자 공간(user가 131µs 더 큼)에서 일어나 자리만 바뀐 것으로 해석
   - 코드 근거: 요청 방향 복사 횟수는 두 버전이 같음. pipe는 사용자→커널→사용자 2회, shm 기본판은 클라이언트→칸(`client_send`), 칸→큐 버퍼(`srv_take`) 2회. 1단계 `shm_bench.c`도 칸→서버 버퍼로 복사해 2회였음
   - 따라서 두 버전의 차이는 복사량이 아니라 시스템 콜과 문맥 교환에서 나옴: 서버 청크당 pipe 5.97회 vs shm 2.02회 (64KB 조각마다 깨어남)
   - 응용에서는 여기에 청크 분석 시간(수백 µs)이 양쪽에 똑같이 더해져 배수가 줄어듦
   - 청크 분석 시간(서버 구간 `proc_ns`)과 요청 지연 비교 [실측값 확인 필요]
2. P5: 차이 크기가 코드 상수로 계산한 세그먼트 크기와 맞음
   - 칸 크기 `CELL_SIZE` = (24 + 262,144)를 64B 단위로 올림 = 262,208B
   - 요청 링 16칸 × 8슬롯 = 32,776kB, 응답 링 4칸 × 8슬롯 = 8,194kB
   - 측정: stats 차이 32,368~32,944kB ≈ 요청 링만, norm 차이 40,448~40,880kB ≈ 요청+응답 링. 통계 모드는 응답 칸에 헤더+32B만 써서 페이지가 거의 안 잡힘
   - 클라이언트 1개인데도 32MB가 잡힌 이유(추정): 서버 하나가 30회를 연달아 받고, 슬롯 번호를 돌아가며 줘서(`next_hint`) 30회 동안 8슬롯을 다 건드림 [확인 필요: 1회만 실행한 서버의 VmHWM]
3. P4: 클라이언트 8개에서 p99 배수가 중앙값 배수보다 작음 (64KB stats 1.18 < 1.66, 256KB stats 1.66 < 2.49, 64KB norm 1.03 < 1.45, 256KB norm 1.44 < 1.67)
   - 8개에서는 양쪽 모두 CPU 경쟁으로 꼬리가 길어져 IPC 차이가 꼬리에서 덜 보임. 근거: 서버 비자발적 문맥 교환 청크당 0.06회(1개) → 0.90회(8개, pipe norm 256KB)

**틀린 부분의 원인 분석**

1. P3 (클라이언트 8개에서 정규화 모드 이득이 오히려 작음)
   - 1단계에 없던 요인: 정규화 계산이 CPU를 많이 씀 + 클라이언트 8개 × 스레드 3개 + 서버 7개 = 약 31개 스레드가 논리 CPU 8개를 나눠 씀
   - 근거 1: shm 서버 user 시간이 청크당 540.7µs(1개) → 1068.4µs(8개). 같은 일을 하는데 CPU 시간이 2배 → 하이퍼스레딩·클럭 경쟁 추정
   - 근거 2: 서버 비자발적 문맥 교환 증가 (위 P4 근거)
   - 근거 3: 정규화 256KB 8개에서 shm 서버 CPU 합계 1158.9µs/청크 vs 통계 256KB 8개 517.0µs → 계산량이 IPC 비용을 덮음
   - 결론(가설): 클라이언트 8개 정규화는 계산 병목이라 IPC 차이가 묻힘
   - [추가 실험 필요] 이 요인만 바꾼 실험: 워커 수만 바꿔 측정 (E3). 예: `scripts/run_app.sh -s 256K -m norm -c 8 -E "-t 2" -T e3_w2`, `-E "-t 8" -T e3_w8`. 워커 수에 따라 pipe/shm 배수가 바뀌면 원인 확인
   - 클라이언트 2개에서 같아진 것: 통계 모드 shm 256KB가 클라이언트 1개(646.5µs)보다 2개(435.0µs)에서 더 빠른 이상값 때문. 1단계 2.4절 4번과 같은 "CPU가 쉬다 깨어나는 비용" 의심 [추가 실험 필요: `taskset`으로 고정한 측정과 비교]
2. P1의 "4KB는 pipe가 약간 앞선다"
   - E0에서 4KB 클라이언트 8개 처리량 pipe 1.16배였지만, 같은 설정을 다시 잰 E1_per·E2_rw_k8에서는 shm이 앞섬 (6.3절 변동 표)
   - 원인: 4KB에서는 두 버전의 서버 CPU(63.1 vs 62.6µs/청크)와 문맥 교환(2.01회)이 같음 → IPC 차이가 측정 간 변동보다 작음
3. E1 (락 범위) 결과 해석 [그림: app_e1_lock_scope.png]
   - per vs table 처리량(청크/s, pipe / shm)
     - stats 4KB: per 23,635 / 27,386, table 31,069 / 31,363
     - stats 256KB: per 3,583 / 4,590, table 3,514 / 6,532
     - norm 4KB: per 14,963 / 25,427, table 28,162 / 28,232
     - norm 256KB: per 2,137 / 2,977, table 2,358 / 2,827
   - 락을 크게 묶은 table이 오히려 빠른 조건이 있음 → 락 범위 효과가 아니라 세션 변동으로 봄. E1_per 자체가 E0와 같은 설정인데 E0보다 느렸음 (stats 4KB pipe 23,635 vs E0 31,405)
   - 결론: 클라이언트 쪽 지표로는 락 범위 차이를 측정 간 변동과 구분 못 함. 락 대기 시간 원자료(`lock_cli_ns`)로 판정해야 함 [실측값 확인 필요: E1 `lock_cli_ns` 중앙값·p99]
4. E2 (전체 통계 락, K) [그림: app_e2_global_lock.png, app_e2_report_lag.png]
   - stats 64KB 클라이언트 8개 shm 처리량: rwlock K=1/8/64 = 17,362 / 18,798 / 18,546, mutex = 12,947 / 13,170 / 17,261
   - stats 4KB 클라이언트 8개: rwlock K=64에서만 두 IPC 모두 느림(pipe 19,618, shm 24,049) → 같은 설정의 mutex K=64(31,011 / 32,227)와 비교하면 그 세션만 느린 것으로 봄
   - 확실한 효과는 K에 따른 통계 반영 지연: 보고 스레드가 본 "클라이언트별 합 − 전체" 중앙값 K=1 0, K=8 14~16, K=64 118~128청크 (최대 2 / 25 / 240) → 워커 4개 × K개만큼 늦게 반영되는 설계와 맞음
   - 결론: 이 응용의 청크 빈도에서는 전체 통계 락이 병목이 아님. K=8은 반영 지연(최대 25청크)이 작고 처리량 손해가 측정 간 변동 안 → 기본값 유지
   - rwlock/mutex 대기 시간(`lock_grd_ns`, `lock_gwr_ns`) 직접 비교 [실측값 확인 필요]

### 6.5 설계 개선과 전후 비교

**개선 내용: shm 제자리 처리 (E5, 서버 `-X inplace`, 커밋 cd0e453)**

- 기본판: 클라이언트 → 요청 칸 → (수신 스레드 복사) 큐 버퍼 → 워커 처리 → (워커 복사) 응답 칸 → (클라이언트 복사) 클라이언트 버퍼
- 개선판: 워커가 요청 칸에서 바로 처리, 정규화 결과도 그 칸에 덮어씀, 응답 칸에는 헤더만 → 클라이언트가 요청 칸에서 복사
  - 정규화 모드 복사 4회 → 2회, 청크마다 하던 malloc/free 없음, 응답 칸 payload 페이지를 안 씀
  - 요청 칸 반환은 응답을 다 읽은 클라이언트가 함 (`REQ_EMPTY`를 클라이언트가 V). 클라이언트는 `seq % 16` 자리에 칸 번호를 적어 두었다가 응답의 seq로 찾음
- 노린 것: 정규화 모드 지연 감소(성능)와 서버 메모리 감소
- 동작 검증: 두 모드 25,600청크 합계 일치, 잘못된 응답 0, `make tsan` 경고 없음, kill -9 정리 확인 (ai_log). E5 본 측정 32조건 합계 일치

**평가**

1. 메모리: 예상대로 확실히 줄어듦
   - 256KB에서 서버 VmHWM이 모든 클라이언트 수에서 8,672~9,984kB 감소 → 응답 링 payload 크기(8,194kB, 6.4절 계산)와 같은 규모
   - 64KB 약 2.1~2.2MB, 4KB 0.2MB 감소 → 응답 칸에서 실제 쓰던 페이지만큼
   - 세그먼트 자체(`SHM_SIZE`)는 그대로 약 40MB. 줄어든 것은 실제로 잡힌 페이지(RSS). 응답 링을 헤더 크기로 줄이면 세그먼트도 줄일 수 있음 → 향후 개선
2. 성능: 일관된 개선이라고 말할 수 없음
   - 256KB c1·c2·c8, 64KB c1은 빨라졌지만, 256KB c4, 64KB c4는 느려짐
   - 기대 효과 크기 추정: 1단계 memcpy_ref 256KB 1스레드 43.70 GB/s 기준 256KB 복사 1회 약 6µs → 2회 줄여도 약 12µs. 측정된 중앙값 변화(256KB에서 −486µs ~ +87µs)가 이보다 훨씬 큼
   - 같은 기본판 설정을 다른 세션에서 잰 값끼리도 20~35% 차이 (norm 256KB c1: E0 667.0 vs E5_base 799.4µs, c8: 1691.6 vs 2286.2µs)
   - → 지연 변화의 대부분은 측정 간 변동으로 봄. 개선판이 c4에서만 느린 원인은 못 찾음 [원인 확인 필요]
3. 결론
   - 메모리 절감 효과는 확인 (256KB 서버 VmHWM 약 −9MB, 약 19%)
   - 성능 효과는 미확정. 다음 실험이 필요: 기본판과 개선판을 번갈아 3회씩(ABABAB) 측정해 세션 변동을 상쇄 [추가 실험 필요]
     - 예: `for i in 1 2 3; do scripts/run_app.sh -i shm -m norm -s "64K 256K" -T e5_base_r$i; scripts/run_app.sh -i shm -m norm -s "64K 256K" -E "-X inplace" -T e5_inplace_r$i; done`
   - 예상과 다른 점: 복사를 줄이면 지연도 줄 것으로 봤으나, 이 노트북에서 256KB 복사 비용(수 µs)은 청크 처리(수백 µs)와 측정 간 변동(수십 %)에 묻힘

### 6.6 IPC 선택 가이드라인

| 조건 | 권장 IPC | 근거 (실험, 수치) |
| --- | --- | --- |
| 작은 응답(통계 모드), 청크 4KB~16KB | 어느 쪽이든 (단순한 pipe 권장) | E0 4KB 중앙값 비 0.94~1.01, 서버 CPU 63.1 vs 62.6µs/청크, 문맥 교환 같음. 순위가 세션마다 바뀜 |
| 큰 청크(64KB~256KB), 통계 모드 | shm | E0 8조건 모두 shm 우위, 중앙값 1.16~2.49배, 클라이언트 8개 256KB 처리량 7,877 vs 3,370 청크/s. pipe는 64KB 조각마다 깨어남(서버 문맥 교환 5.97 vs 2.02회/청크) |
| 큰 응답(정규화 모드), 64KB~256KB | shm | 256KB 클라이언트 1개 중앙값 1539.4 vs 667.0µs(2.31배), 서버 CPU 1059.1 vs 594.5µs/청크 |
| 클라이언트 수가 많을 때(8개) | shm (단, 이득은 줄어듦) | 64KB 이상 처리량 1.24~2.34배 유지. 정규화 256KB는 계산 병목으로 배수가 1.49배로 줄어듦 |
| 메모리가 제한될 때 | pipe, 또는 shm 제자리 처리 | 256KB에서 shm 서버 VmHWM이 pipe보다 32~40MB 큼. E5 제자리 처리로 약 9MB 줄어듦 |
| 작은 메시지를 아주 많이 보낼 때 | pipe (shm이면 링을 16칸 이상) | 1단계 64B 처리량 pipe 1,533,299 vs shm 4칸 117,242 msg/s. 16칸으로 1,485,383 |

- 우리 응용(녹음 파일 일괄 분석, 청크 64KB 이상)에는 shm이 맞음. 4~16KB 청크만 쓴다면 구현이 단순한 pipe도 충분

## 8. 결론 및 총평

### 8.1 결론 및 총평

- 목표 달성
  1. 1단계: 5개 크기 × 4개 클라이언트 수로 pipe/shm의 지연·처리량·자원을 측정. 작은 메시지 shm 열세의 원인(링 4칸)을 추가 실험으로 확인
  2. 예측 P1~P5 중 P2·P5 일치, P1·P4는 범위를 좁히면 일치, P3는 부분 일치
  3. 2버전 모두 136조건에서 합계 일치, 잘못된 응답 0, IPC 자원 남지 않음
  4. 설계 개선 1회(E5): 메모리 감소 확인, 지연 개선은 미확정
- 배운 점
  1. 1단계 배수(256KB 5.6배)가 응용에서는 1.16~2.49배로 줄어듦. 응용에서는 같은 청크 분석 시간이 양쪽에 더해지기 때문
  2. pipe의 비용은 복사보다 64KB 조각마다 생기는 문맥 교환에서 크게 드러남 (서버 CPU 합계는 비슷한데 문맥 교환은 3배)
  3. WSL2 노트북에서 같은 설정의 결과가 세션마다 수십 % 다름. 비교할 두 조건은 연달아, 여러 번 번갈아 재야 함
- 한계
  1. 서버 구간 시간(큐 대기, 처리, 락 대기) 원자료 미반영
  2. P3 실패 원인(계산 병목)과 클라이언트 1개 이상값(깨어나는 비용)은 가설이고 확인 실험 미실시
  3. 창 크기 4, 섞인 크기 분포, E3(큐·워커), E4(pipe 버퍼 1MB) 미측정
- 향후 개선
  1. E5 ABAB 반복 측정, E3 워커 수 실험, E4 `F_SETPIPE_SZ` 1MB
  2. shm 응답 링을 헤더 크기로 줄여 세그먼트 자체를 약 8MB 축소
  3. `strace -c`로 버전별 read/write/semop 호출 수 비교
